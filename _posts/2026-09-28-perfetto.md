# Origem e Propósito

O Perfetto nasceu dentro do Google como substituto do Systrace no Android. O Systrace era baseado no `ftrace` do kernel Linux e produzia traces em formato HTML fixo, difíceis de processar programaticamente e sem suporte a eventos de aplicação. A primeira versão estável do Perfetto foi integrada ao Android 9 (Pie, 2018) e tornou-se a ferramenta padrão de tracing no Android a partir do Android 10.

O que o diferencia da geração anterior:

- **Formato binário compacto (protobuf)**: traces de produção podem ser coletados com overhead de memória controlado, mesmo em dispositivos com poucos recursos.
- **SDK de instrumentação multiplataforma**: roda em Android, Linux, macOS e Windows. O mesmo trace pode combinar eventos do kernel (via `ftrace`), do sistema operacional, e da aplicação C++.
- **Trace Processor**: motor SQL embutido que interpreta o trace. Permite queries como "qual stack estava ativa quando o jitter de frame ultrapassou 16 ms?".
- **Interface web em `ui.perfetto.dev`**: visualizador de linha do tempo que carrega arquivos locais sem enviar dados a servidores.

O Perfetto não substitui `perf` nem profilers de amostragem: ele complementa. Use `perf` para encontrar funções quentes; use o Perfetto para entender a sequência de eventos que leva a um pico de latência.

# Arquitetura

```
┌──────────────────────────────────────────────────────┐
│                   Sua Aplicação C++                  │
│  TRACE_EVENT / counters / flows  →  SDK do Perfetto  │
└───────────────────────┬──────────────────────────────┘
                        │ IPC (Unix socket / in-process)
               ┌────────▼────────┐
               │     traced      │  daemon de tracing
               │  (ring buffer)  │
               └────────┬────────┘
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
   traced_probes    ftrace plugin   heapprofd
   (sysfs, /proc)   (kernel events) (heap profiler)
                        │
               ┌────────▼────────┐
               │  .perfetto-trace │  arquivo binário
               └────────┬────────┘
                        │
         ┌──────────────▼──────────────┐
         │       Trace Processor        │  motor SQL
         └──────────────┬──────────────┘
                        │
              ui.perfetto.dev / Python / C++
```

Em modo *in-process* (o mais comum em programas autônomos), o daemon `traced` não é necessário: a SDK grava o trace diretamente em memória e você serializa para arquivo ao final. Isso simplifica a integração em ferramentas de linha de comando e em testes.

# Integração da SDK C++

## Obtendo a SDK

O Perfetto distribui uma SDK amalgamada: dois arquivos (`perfetto.h` e `perfetto.cc`) que encapsulam toda a implementação. É a forma mais simples de integrar sem depender do sistema de build do projeto principal.

```bash
# Clonar o repositório e gerar o amalgamado
git clone https://android.googlesource.com/platform/external/perfetto
cd perfetto
python3 tools/gen_amalgamated --output sdk/perfetto
```

Isso gera `sdk/perfetto.h` e `sdk/perfetto.cc`. Adicione os dois ao seu projeto.

### Via CMake FetchContent

```cmake
include(FetchContent)
FetchContent_Declare(
  perfetto
  GIT_REPOSITORY https://android.googlesource.com/platform/external/perfetto
  GIT_TAG        v47.0
)
FetchContent_MakeAvailable(perfetto)

target_link_libraries(meu_programa PRIVATE perfetto)
```

## Definindo Categorias

Categorias são o mecanismo de filtragem do Perfetto. Elas permitem habilitar apenas os subsistemas que importam em uma sessão, zerando o overhead dos demais.

```cpp
// tracing_categories.h  — inclua em todos os arquivos que emitem traces
#include <perfetto.h>

PERFETTO_DEFINE_CATEGORIES(
    perfetto::Category("rendering")
        .SetDescription("Pipeline de renderização"),
    perfetto::Category("physics")
        .SetDescription("Simulação física"),
    perfetto::Category("io")
        .SetDescription("Operações de disco e rede"),
    perfetto::Category("debug")
        .SetDescription("Eventos de diagnóstico — não ativar em produção")
);
```

```cpp
// tracing_categories.cc  — compile exatamente uma vez
#include "tracing_categories.h"
PERFETTO_TRACK_EVENT_STATIC_STORAGE();
```

A macro `PERFETTO_TRACK_EVENT_STATIC_STORAGE` instancia o armazenamento estático necessário para os contadores internos da SDK. Omiti-la causa erros de linker.

## Inicializando o Tracing

```cpp
#include "tracing_categories.h"

void init_perfetto() {
    perfetto::TracingInitArgs args;
    args.backends = perfetto::kInProcessBackend;
    perfetto::Tracing::Initialize(args);
    perfetto::TrackEvent::Register();
}
```

`kInProcessBackend` é adequado para programas autônomos. Em Android ou quando você precisa integrar com `traced` do sistema, use `kSystemBackend` ou `kInProcessBackend | kSystemBackend`.

## Iniciando e Encerrando uma Sessão

```cpp
std::unique_ptr<perfetto::TracingSession> start_tracing() {
    perfetto::TraceConfig cfg;
    cfg.add_buffers()->set_size_kb(8192);

    auto* ds_cfg = cfg.add_data_sources()->mutable_config();
    ds_cfg->set_name("track_event");

    // Ativar apenas as categorias que interessam
    perfetto::protos::gen::TrackEventConfig te_cfg;
    te_cfg.add_enabled_categories("rendering");
    te_cfg.add_enabled_categories("physics");
    ds_cfg->set_track_event_config_raw(te_cfg.SerializeAsString());

    auto session = perfetto::Tracing::NewTrace();
    session->Setup(cfg);
    session->StartBlocking();
    return session;
}

void stop_tracing(std::unique_ptr<perfetto::TracingSession> session,
                  const std::string& path) {
    session->StopBlocking();

    std::vector<char> trace_data(session->ReadTraceBlocking());

    std::ofstream out(path, std::ios::binary);
    out.write(trace_data.data(), static_cast<std::streamsize>(trace_data.size()));
}
```

```cpp
int main() {
    init_perfetto();
    auto session = start_tracing();

    run_frame();  // código instrumentado

    stop_tracing(std::move(session), "trace.perfetto-trace");
}
```

## Eventos de Duração

O `TRACE_EVENT` mede o tempo de uma região de código usando RAII: o evento abre no ponto da macro e fecha ao sair do escopo.

```cpp
void render_frame() {
    TRACE_EVENT("rendering", "render_frame");

    {
        TRACE_EVENT("rendering", "culling");
        cull_objects();
    }

    {
        TRACE_EVENT("rendering", "draw_calls");
        submit_draw_calls();
    }
}
```

Para funções cujo nome é dado por uma string dinâmica — cuidado: formatar strings dentro de eventos de alta frequência introduz overhead significativo:

```cpp
void dispatch(const Command& cmd) {
    // Ruim: aloca string a cada chamada
    TRACE_EVENT("io", "dispatch", "command", cmd.name());

    // Bom: usa literal diretamente quando possível
    TRACE_EVENT("io", "dispatch_write");
}
```

## Eventos Instantâneos e Contadores

Eventos instantâneos marcam pontos no tempo sem duração:

```cpp
void on_frame_dropped() {
    TRACE_EVENT_INSTANT("rendering", "frame_dropped",
                        perfetto::Track::Global(0));
}
```

Contadores rastreiam valores numéricos ao longo do tempo, ideais para filas, uso de memória e FPS:

```cpp
void update_stats(size_t queue_depth, float fps) {
    TRACE_COUNTER("rendering", "queue_depth",
                  static_cast<int64_t>(queue_depth));
    TRACE_COUNTER("rendering", "fps",
                  static_cast<int64_t>(fps));
}
```

No visualizador, contadores aparecem como gráficos contínuos na linha do tempo — muito mais informativos do que eventos de duração para grandezas que variam suavemente.

## Flow Events: Conectando Trabalho Assíncrono

O maior ponto cego em sistemas assíncronos é a causalidade: qual tarefa enfileirou este trabalho? O Perfetto resolve isso com *flow events*, que desenham setas entre eventos em threads ou processos diferentes.

```cpp
#include <atomic>

std::atomic<uint64_t> flow_id_counter{1};

void producer_thread() {
    uint64_t id = flow_id_counter.fetch_add(1);

    {
        TRACE_EVENT("io", "enqueue_work");
        TRACE_FLOW_BEGIN("io", "work_item", id);  // início do flow
        queue.push({id, make_work_item()});
    }
}

void consumer_thread() {
    auto [id, item] = queue.pop();

    TRACE_FLOW_END("io", "work_item", id);  // fim do flow
    TRACE_EVENT("io", "process_work");
    process(item);
}
```

No visualizador, uma seta conecta `enqueue_work` no thread produtor ao `process_work` no thread consumidor, mostrando exatamente o caminho causal de cada unidade de trabalho.

## Tracks Customizadas

Por padrão, eventos aparecem na track do thread atual. Para agrupar eventos de objetos independentemente da thread:

```cpp
class RenderPass {
    perfetto::Track track_;

public:
    explicit RenderPass(uint64_t id)
        : track_(perfetto::Track(id)) {
        auto desc = track_.Serialize();
        desc.set_name("RenderPass " + std::to_string(id));
        perfetto::TrackEvent::SetTrackDescriptor(track_, desc);
    }

    void execute() {
        TRACE_EVENT("rendering", "RenderPass::execute", track_);
        // ...
    }
};
```

Tracks customizadas permitem rastrear o ciclo de vida de objetos de longa duração que passam por múltiplas threads.

## Argumentos Tipados

Argumentos adicionam contexto a um evento sem criar eventos separados:

```cpp
void load_texture(const std::string& path, int width, int height) {
    TRACE_EVENT("rendering", "load_texture",
        "path", path,
        "width", width,
        "height", height);
    // ...
}
```

No visualizador, clicar no evento exibe esses campos no painel de detalhes. Prefira tipos primitivos (`int`, `uint64_t`, `double`, `bool`) a strings formatadas para evitar alocações.

## Queries SQL com o Trace Processor

O Trace Processor expõe o trace como um banco de dados SQLite. Acesse pela aba *Query (SQL)* no visualizador.

### Frames mais lentos

```sql
SELECT
  name,
  dur / 1e6 AS dur_ms,
  ts / 1e6 AS start_ms
FROM slice
WHERE name = 'render_frame'
ORDER BY dur DESC
LIMIT 20;
```

### Distribuição de latência

```sql
SELECT
  CAST(dur / 1e6 AS INT) AS bucket_ms,
  COUNT(*) AS count
FROM slice
WHERE name = 'render_frame'
GROUP BY bucket_ms
ORDER BY bucket_ms;
```

### Eventos que ultrapassaram threshold

```sql
SELECT
  s.name,
  s.dur / 1e6 AS dur_ms,
  t.name AS thread_name
FROM slice s
JOIN thread_track tt ON s.track_id = tt.id
JOIN thread t ON tt.utid = t.utid
WHERE s.name GLOB 'physics*'
  AND s.dur > 5e6  -- mais de 5 ms
ORDER BY s.dur DESC;
```

### Contadores ao longo do tempo

```sql
SELECT
  ts / 1e9 AS t_sec,
  value
FROM counter c
JOIN counter_track ct ON c.track_id = ct.id
WHERE ct.name = 'queue_depth'
ORDER BY ts;
```

Para análise em lote ou integração com CI:


```python
from perfetto.trace_processor import TraceProcessor

tp = TraceProcessor(trace="trace.perfetto-trace")

    FROM slice
    WHERE name GLOB 'render*'
```

# Tracing com `traced` do Sistema (Linux)

Em vez de gravar em memória dentro do processo, você pode conectar ao daemon `traced` para capturar múltiplos processos simultaneamente, incluindo eventos do kernel via `ftrace`.

```bash
# Iniciar os daemons (uma vez por sessão)
traced &
traced_probes &

# Iniciar trace com configuração em protobuf texto
perfetto \
  -c - --txt \
  -o trace.perfetto-trace \
  <<EOF
buffers: { size_kb: 32768 }
data_sources: {
  config {
    name: "track_event"
    track_event_config {
      enabled_categories: "rendering"
      enabled_categories: "physics"
    }
  }
}
data_sources: {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      ftrace_events: "power/cpu_frequency"
    }
  }
}
duration_ms: 5000
EOF
```

Com `sched_switch`, o trace mostra exatamente quando cada thread foi preemptado ou saiu voluntariamente do CPU — indispensável para diagnosticar latência causada pelo scheduler, não pelo código da aplicação.

# Overhead e Controle de Custo

O overhead do Perfetto em eventos desabilitados é praticamente zero: a SDK usa uma verificação atômica de um bit por categoria antes de qualquer trabalho. Em eventos habilitados, o custo típico é de 50–200 ns por evento, dependendo do número de argumentos.

## Nunca instrumente dentro de loops internos

```cpp
// Ruim: 10 milhões de eventos por frame em dados grandes
for (const auto& vertex : mesh.vertices()) {
    TRACE_EVENT("rendering", "process_vertex");  // não faça isso
    transform(vertex);
}

// Bom: trace engloba o loop inteiro
void process_mesh(const Mesh& mesh) {
    TRACE_EVENT("rendering", "process_mesh",
        "vertex_count", mesh.vertex_count());
    for (const auto& vertex : mesh.vertices())
        transform(vertex);
}
```

## Prefira categorias de debug desabilitadas em produção

```cpp
// Eventos de diagnóstico caros ficam na categoria "debug"
void expensive_validation() {
    TRACE_EVENT("debug", "validate_scene_graph");
    validate();
}
```

Na configuração de produção, não inclua `"debug"` em `enabled_categories`. O custo é apenas o teste do bit atômico.

## Limite o tamanho do ring buffer

Ring buffers maiores reduzem a chance de perder eventos, mas consomem memória. Para um trace de 5 segundos de um sistema de 60 FPS:

```cpp
cfg.add_buffers()->set_size_kb(16384);  // 16 MB cobre a maioria dos casos
```

Se eventos estiverem sendo descartados, o Trace Processor reporta `buffer_cloned` ou gaps na linha do tempo.

# Integração com Testes de Regressão

O Trace Processor via Python permite verificar invariantes de performance em testes automatizados:

```python
import unittest
from perfetto.trace_processor import TraceProcessor

class PerformanceTest(unittest.TestCase):
    def setUp(self):
        self.tp = TraceProcessor(trace="test_trace.perfetto-trace")

    def test_frame_time_p99(self):
        df = self.tp.query("""
            SELECT dur / 1e6 AS ms
            FROM slice
            WHERE name = 'render_frame'
            ORDER BY ms
        """).as_pandas_dataframe()

        p99 = df['ms'].quantile(0.99)
        self.assertLess(p99, 16.6, f"p99 frame time = {p99:.1f} ms (> 16.6 ms)")

    def test_no_frame_over_50ms(self):
        df = self.tp.query("""
            SELECT COUNT(*) AS n FROM slice
            WHERE name = 'render_frame' AND dur > 50e6
        """).as_pandas_dataframe()

        self.assertEqual(df['n'].iloc[0], 0, "Frames acima de 50 ms detectados")
```

Execute o programa com tracing ativado, salve o trace, e rode os testes em CI. Regressões de latência ficam visíveis antes de chegarem à produção.

# Comparando com Alternativas

| Ferramenta | Foco | Instrumentação manual | Visualização causal | SQL sobre o trace |
|:-----------|:-----|:---------------------:|:-------------------:|:-----------------:|
| **Perfetto** | Tracing de sistema e aplicação | SDK C++ | Sim (flow events) | Sim (Trace Processor) |
| `perf` | Profiling de CPU | Não (amostragem) | Não | Não |
| Google Benchmark | Microbenchmarks | Explícita (loop) | Não | Não |
| Tracy | Tracing em tempo real | SDK C++ | Parcial | Não |
| Jaeger / Zipkin | Distributed tracing | SDK por linguagem | Sim (spans) | Não |
| Chrome Tracing | Tracing de browser | `trace_event` JSON | Sim | Não |

O Perfetto ocupa o espaço entre profilers de amostragem (`perf`) e systems de distributed tracing (Jaeger): instrumentação de baixo overhead com semântica de linha do tempo e análise programável.

# Boas Práticas: Checklist

**Estrutura de categorias**
- [ ] Categorias refletem subsistemas, não funções individuais
- [ ] Categoria `"debug"` separada para eventos de diagnóstico caros
- [ ] Configuração de produção lista apenas categorias necessárias

**Instrumentação**
- [ ] `TRACE_EVENT` em funções de duração significativa (> 0,1 ms), não em loops internos
- [ ] Contadores (`TRACE_COUNTER`) para grandezas numéricas contínuas
- [ ] Flow events em toda transferência de trabalho entre threads
- [ ] Argumentos com tipos primitivos; strings apenas quando o valor for estático ou raro

**Coleta**
- [ ] Ring buffer dimensionado para cobrir a janela de interesse
- [ ] Em análises de scheduler: `ftrace sched_switch` habilitado
- [ ] Traces salvos com timestamp no nome para rastreabilidade

**Análise**
- [ ] Queries SQL para P50/P95/P99 de eventos críticos
- [ ] Testes de regressão de performance via Trace Processor em CI
- [ ] Correlação visual: frames lentos → stack de frames → counters no mesmo instante

# Exemplo Completo: Game Loop Instrumentado

```cpp
// main.cpp
#include "tracing_categories.h"
#include <fstream>
#include <thread>

PERFETTO_TRACK_EVENT_STATIC_STORAGE();

void physics_update(float dt) {
    TRACE_EVENT("physics", "physics_update", "dt_ms", dt * 1000.f);
    simulate_collisions(dt);
    integrate_velocities(dt);
}

void render_frame(uint64_t frame_id) {
    TRACE_EVENT("rendering", "render_frame", "frame", frame_id);
    TRACE_COUNTER("rendering", "draw_calls", count_draw_calls());

    {
        TRACE_EVENT("rendering", "visibility_cull");
        cull_frustum();
    }
    {
        TRACE_EVENT("rendering", "gpu_submit");
        submit_commands();
    }
}

int main() {
    perfetto::TracingInitArgs args;
    args.backends = perfetto::kInProcessBackend;
    perfetto::Tracing::Initialize(args);
    perfetto::TrackEvent::Register();

    perfetto::TraceConfig cfg;
    cfg.add_buffers()->set_size_kb(16384);
    auto* ds = cfg.add_data_sources()->mutable_config();
    ds->set_name("track_event");

    perfetto::protos::gen::TrackEventConfig te_cfg;
    te_cfg.add_enabled_categories("rendering");
    te_cfg.add_enabled_categories("physics");
    ds->set_track_event_config_raw(te_cfg.SerializeAsString());

    auto session = perfetto::Tracing::NewTrace();
    session->Setup(cfg);
    session->StartBlocking();

    constexpr float dt = 1.f / 60.f;
    for (uint64_t frame = 0; frame < 300; ++frame) {  // 5 segundos
        physics_update(dt);
        render_frame(frame);
        std::this_thread::sleep_for(std::chrono::milliseconds(16));
    }

    session->StopBlocking();
    auto data = session->ReadTraceBlocking();
    std::ofstream out("game_loop.perfetto-trace", std::ios::binary);
    out.write(data.data(), static_cast<std::streamsize>(data.size()));
}
```

Abra `game_loop.perfetto-trace` em `ui.perfetto.dev`. Você verá as tracks de física e renderização por frame, os contadores de draw calls, e qualquer spike de latência imediatamente visível como uma barra mais larga na linha do tempo.

---

A instrumentação certa transforma diagnóstico de performance de adivinhação em investigação. Com `perf` você encontra onde o tempo vai; com Google Benchmark você quantifica variantes; com Perfetto você entende *por que* eventos específicos demoram o que demoram — e qual sequência de causas levou até eles.
